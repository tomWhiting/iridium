# Soft wrap — kernel design

Produced by a 16-agent design workflow on 2026-07-30: four parallel readers
mapped the current viewport/fold/motion/consumer contract, three designers
argued independent angles, and three adversarial judges scored each design on
correctness, blast radius, feel, performance and hygiene.

**Winner: `new-vocabulary`** (108 points, against 94 for `lazy-windowed` and 91
for `unified-mapping`). Every judge found a real flaw in every design; the
flaws in this one are listed below and MUST be fixed before implementation.

Decision context: soft wrap is settled — yes, default on, toggleable, and it
lives in the kernel so all three faces agree where a line wraps. This document
is about *how*.

## Summary

Soft wrap enters the kernel as a new, parallel coordinate space called the **screen row**, in a new `crate::layout` module; the existing fold "visual line" space (`FoldState::visual_to_document_line` / `document_to_visual_line`, their `Editor` re-exports and their napi/wasm exports) keeps its exact name, signature, meaning and serialized shape, so nothing outside the kernel breaks. Rows are composed from two independent pieces: a fold-free per-document-line row count index (`WrapIndex`, keyed by document line and invalidated only by edits and wrap params) and a coalesced fold-interval row prefix sum (`FoldRowSums`, rebuilt only on fold toggles), so a fold change never invalidates a measurement and an edit never rebuilds fold sums. `Viewport` is not modified at all — it keeps meaning fold-visual lines and keeps its serde shape, which is a feature: a persisted session stores a *line*, not a row, so reopening at a different window width lands on the right text; a new `RowViewport` carries the row-space scroll anchor with explicit, tested bridges in both directions. Widths are measured in **cells** (`unicode-width` semantics plus tab stops anchored at the row's screen column zero), which is the only unit that lets the GPU faces and the terminal face agree on break points by construction — and it lets the GPU faces set `Wrap::None` and delete the entire ad-hoc wrap model currently living in `wasm.rs` (`cached_visual_line_map`, `visual_lines_per_logical_line`, `extra_wrap_lines`). Caret-at-a-break ambiguity is resolved by a `RowAffinity` bit stored beside the sticky-column state on `KeyboardHandler`, never inside `Position`/`Selection`/`CursorState`, so command inversion, undo and the `HashMap<Position, _>` in the multi-cursor path are untouched. Two changes are genuinely not additive and must be accepted: `apply_command_internal` must call `RowIndex::apply_edit` (the wrap cache must not inherit the fold module's never-invalidated-on-edit discipline), and the sticky vertical column becomes a sticky *cell* with a fifth validity key, a layout generation, that a resize/font change/undo-with-changed-layout invalidates.

## The model

## Three spaces, three nouns, no overloading

| Space | Newtype | Cardinality vs document line | Owner | Status |
|---|---|---|---|---|
| **Document line** | `DocLine(usize)` | 1:1 | `Document`/`Rope` | unchanged |
| **Visual line** | (bare `usize`, as today) | 1:1-or-hidden | `FoldState` | **frozen — not touched** |
| **Screen row** | `ScreenRow(usize)` | 1:N (hidden lines have none) | `layout::RowIndex` | new |
| **Cell** | `Cells(u32)` | horizontal unit | `layout::width` | new |

The word "visual" is never used for wrap anywhere in the new module, its docs, its tests, or its bindings. `render/text.rs`'s third meaning (cosmic-text layout runs) disappears, because faces stop asking cosmic-text to wrap.

## The composition law

Rows are composed **directly from document lines**, not through the fold visual space:

```
rows_before_doc(d) = wrap.prefix_rows(d) − folds.hidden_rows_before_doc(d)
```

The only `FoldState` operations the row layer consumes are `is_line_hidden(usize) -> bool` (a pure interval-containment predicate, correct even under nested folds), plus `folded_lines()` + `region_at()` to enumerate intervals, which are **coalesced into disjoint intervals** before summing.

Deliberate: `FoldState`'s own prefix sums (`hidden_before`/`hidden_count`, `fold_state.rs:70-79`) double-count under nested folds because `fold_all` (`fold_state.rs:469-474`) folds nested regions and `LineMapping::build` sums spans unconditionally. Routing rows through `visual_to_document_line` would inherit that. Routing rows through `is_line_hidden` + coalesced intervals is correct by construction.

`row_columns` and `caret_limit` are **two different answers on purpose**:
- `row_columns(row_i)` = `start_i .. start_{i+1}` — contiguous, half-open, partitions `0..=line_len` across the line's rows with no gap and no overlap. This is what selection painting and text extraction use.
- `caret_limit(row_i)` = `start_{i+1} − (trailing break-consumed whitespace)` — where a click at the far right of the row lands. Collapsing these two is the single most common wrap bug: a click past the end of a word-wrapped row jumps to the next row.

At `row_height = 1.0` this is the terminal cell grid, exactly as `Viewport` already is.

Both clamps that stand between this call and ropey's `assert!(line_idx <= len_lines)` panic (`viewport.rs:322-323`) are preserved and each has a named test.

## Affinity: where the bit lives

At a break column `c` (the start of row `i > 0`), `c` is simultaneously the end of row `i−1` and the start of row `i`. `place(pos, Leading)` → `(row i, cell 0)`. `place(pos, Trailing)` → `(row i−1, cell = content width of row i−1)`. For every other column, affinity is ignored.

`RowAffinity` is stored as one field on `KeyboardHandler` (beside `preferred_columns`/`sticky_state`) and read via `Editor::caret_affinity()`. It is **not** in `Position`, `Selection` or `CursorState`, so: `Position`'s `Eq`/`Hash` are untouched (the `HashMap<Position, usize>` at `multi_cursor_verbs.rs:276` still works), `Position::advanced_through` (the command-inversion source of truth) is untouched, no serialized cursor format changes, and undo cannot restore a stale affinity — it resets to `Leading`, which is the safe answer.

Set to `Trailing` by: `End`, a rightward motion that lands exactly on a break column, and a click in the trailing region of a row. Reset to `Leading` by everything else, wired to the same `reset_vertical_state()` sites that already exist (13 in `editor/core.rs`, 13 in `wasm.rs`).

## Layout generation

`LayoutGeneration` is a monotone `u64` on `RowIndex`, bumped by `apply_edit`, `set_params` and `on_folds_changed`. It is the fifth key in the sticky-column reusability conjunction at `navigation.rs:116-122` — the one thing `CursorState` equality and `Document::revision()` cannot express, because a window resize, a font-size change or a wrap toggle changes layout while leaving both byte-identical.

## Wrap rules

## The scanner

One greedy left-to-right pass over the line's chars, carrying `(char_col, cells_in_row, last_break_opportunity)`. `effective = params.columns.max(1)` — so **width 0 is treated as width 1** and nothing ever divides by the wrap width (the algorithm is a scan, not a division).

Per row:
1. `cells = indent` where `indent = 0` on row 0 and, on continuation rows, `min(leading_indent_cells(line), effective / 2)` under `IndentMode::MatchLeading`. The halving is the width-1 guard: at `effective = 1` the indent is 0, so at least one content cell always remains.
2. Consume chars, accumulating `w = CellWidth::of(ch, cells)`.
3. A char **fits** iff `cells + w <= effective`.
4. If it does not fit:
   - **row is still empty** (`char_col == row_start_col`, ignoring the indent) → place it anyway, let it overflow, end the row after it. This is the unconditional **progress guarantee**; without it width 1 + a double-width char is an infinite loop.
   - otherwise → break.
5. **Break point.** `WrapMode::Word`: break at the char after the last break opportunity at or before the overflowing char; a break opportunity is the position after a run of spaces/tabs, or after any of `-` `/` `,` `)` `]` `}` (a small, documented set chosen for JSON paths and prose, not a Unicode line-breaking algorithm). If the row contains no opportunity, fall back to a character break at the overflowing char. `WrapMode::Character`: always break at the overflowing char.
6. **A break is never emitted at `line_len`.** The scan terminates when `char_col == line_len`; the row in progress is the last row and no break column is pushed.
7. A hard ceiling `rows <= line_len + 1` is asserted in the scanner's loop condition (as a bound, not a `panic!`), so a rule regression terminates instead of hanging the render thread.

## The named hard cases

**Last row exactly full.** A line whose total width is exactly `effective` produces **1 row**, not 2. A line of `2 * effective` produces exactly 2. This falls directly out of rule 6: the scan never has a "doesn't fit" event, because it ends when the chars run out. The naive implementation computes `ceil(width / effective)` and emits a trailing empty row, which then renders as a phantom blank line and adds 1 to every subsequent row index in the document. Named regression test.

**Trailing whitespace at a word break.** The spaces consumed by the break belong to the **preceding** row's column range. `row_columns(i) = start_i .. start_{i+1}` is contiguous and covers them, so selection painting and text extraction have no gap; the face clips whatever hangs past `effective` cells. `caret_limit(i)` excludes them, so a click at the far right of row `i` lands after the last visible glyph rather than on row `i+1`.

**Tabs.** A tab's advance is `tab_width - (cells_in_row % tab_width)`, minimum 1, where `cells_in_row` **includes the continuation indent**. Tab stops are therefore anchored at the row's screen column zero, which is what a terminal does and what the GPU face must do for the two to agree. A tab is **atomic and never split**: if it does not fit it goes to the next row (rule 4). A tab at the row start that still does not fit (`effective < tab_width`) has its advance **clamped to `effective - cells`** so it fills the row exactly, and the row ends after it — the general rule for any atomic unit wider than a whole row. Naive failure: expanding the tab to `tab_width` unconditionally, so the row overflows by up to 3 cells and the terminal face wraps a second time on its own.

**Double-width CJK in the final cell.** At `cells = effective - 1` with a Wide next char (`w = 2`), `cells + w > effective` → break before it. Row `i` ends with **one unused cell**, which the terminal leaves blank and the GPU face leaves empty. `"aaa世"` at `effective = 4` is `["aaa", "世"]`. Naive failures: (a) measuring in chars, so the row holds 4 "characters" and the terminal wraps a second time producing a phantom row; (b) splitting the character, which is impossible in a char-column model and produces an unaddressable position.

**Width 1.** `effective = 1`, indent 0. Every non-zero-width char gets its own row; a Wide char overflows to 2 cells on its own row via rule 4a. Row count equals the number of non-zero-width chars (minimum 1). Terminates by construction.

**Width 0.** Clamped to 1 by `effective = params.columns.max(1)`. `columns == 0` is separately the sentinel for **wrap disabled**, checked before the scanner is ever called: `WrapIndex` short-circuits to `rows(d) = 1` for every line, and every mapping degenerates to the identity over visible lines. So "width 0" never reaches the scanner in practice; the `.max(1)` is the belt to that braces.

**Zero-width and combining marks.** `CellWidth::of` returns 0 cells for `Mn`/`Me`/`Cf` and for control characters. Two structural rules follow: (a) a zero-width char **never starts a row** — it is glued to its predecessor, so `"e" + U+0301` never splits; (b) the scanner **never breaks immediately after** a ZWJ (U+200D) or a variation selector (U+FE0E/U+FE0F). Together these cover combining accents and the common emoji-ZWJ case without a grapheme-segmentation dependency. Zero-width chars are also not addressable by `position_at` (you cannot click between a base and its mark), which is correct.

**East Asian Ambiguous** is measured as **1 cell**, unconditionally and non-configurably. Making it configurable is a rabbit hole whose only correct answer requires knowing the user's terminal font; picking 1 and documenting it is the honest choice.

**Empty line.** 1 row, `row_columns = 0..0`, `caret_limit = 0`. Not zero rows — a zero-row line would break the strict monotonicity of `line_of_row`.

**A fold that starts mid-wrapped-line** cannot happen: `FoldRegion` is line-granular (`start_line`/`end_line`, with `start_line` visible and `start+1..=end` hidden — the strict `>` at `fold_state.rs:131`). The real case is a **folded start line that itself wraps**: it keeps all `N` of its rows, and the `… }` placeholder is drawn at the end of its **last** row. The placeholder is explicitly **not** wrap-affecting — it may overflow the wrap width. That is a deliberate trade: making it wrap-affecting would couple the wrap measurement cache to fold state and destroy the property that a fold toggle never invalidates a measurement. Listed as a weakness.

## Motion semantics

## Up / Down — row motion with a sticky cell

`vertical_move_by_row` moves the caret one **screen row**, not one document line. Cross-line movement is implicit: moving down from the last row of line `d` lands on row 0 of the next *visible* line (fold-hidden lines are skipped for free, because they have no rows).

The sticky quantity is a **cell offset within the row**, including the continuation indent, so the caret tracks a straight vertical line down the screen through rows of differing content. This is the single most important decision, and it is why the four existing seed sites (`navigation.rs:81`, `:132`, `multi_cursor_verbs.rs:236`, `:281`) must stop reading `sel.head.column` and start calling `RowIndex::place(pos, affinity).cell`. Keeping the field's `usize` type and reinterpreting its unit is the exact silent bug the map warns about: on an unwrapped line the two coincide, so every existing test passes, and on row 3 of a wrapped JSONL record the seed is hundreds of columns wrong.

Edge cases, translated exactly from the documented contract at `motions.rs:229-236`:
- Up on the **first row of the document** → `(Position::zero(), Cells(0))`, sticky reset to 0.
- Down on the **last row of the document** → document end, sticky reset to that end cell.
- Down on the last *document line* but **not** its last row now moves to the next row. The naive port checks `head.line >= last_line` and snaps to document end, teleporting the caret over the remaining 29 rows of a wrapped JSONL record — precisely the workload this editor exists for.

Landing column: `position_at(target_row, sticky_cell)` clamps `sticky_cell` to `caret_limit(target_row)` — **not** to `document.line_len(line)`. Clamping a cell against a whole document line's char count (`motions.rs:252`, `:267`) is far too permissive on a wrapped line and places the caret past the end of the row it was supposed to land on, which then renders at the start of the *next* row and gets misdiagnosed as a renderer bug.

`handle_add_cursor_vertical` (`multi_cursor_verbs.rs:237-253`) is a second, independent implementation of vertical movement that inlines `head.line ± 1`. It is rewritten to call `vertical_move_by_row` so the two cannot diverge; that is the whole reason it must be touched.

## Home / End

Both become row-relative, in a way that is provably identical to today whenever the line occupies one row:
- **End** → `caret_limit(current_row)` with affinity `Trailing`. On the final row this equals `motions::line_end` exactly.
- **Home** (smart) → on row 0 of a line, byte-identical to `motions::line_start_smart` (toggle between the document line's first non-whitespace and column 0). On a continuation row, toggle between the **row's** first non-whitespace and the **row's** start column. A three-state cycle across the row and the line was considered and rejected as fussy and untestable.
- `Ctrl+Home` / `Ctrl+End` (document start/end) are unchanged — they are document motions and must stay so.

## Word motion — deliberately unchanged

`word_left`/`word_right` stay **document-based and wrap-agnostic**. A wrap point is not a word boundary, and a break can fall inside a word under `WrapMode::Character`. `word_left` at column 0 still goes to the end of the previous *document* line (`motions.rs:98-108`), which renders on that line's last row — which is exactly what a user expects. Zero changes to `motions.rs`'s word functions.

Adjacent, flagged, not fixed here: `word_left`/`word_right`/`select_word_at` each materialise the whole document line into a `Vec<char>` per cursor per keystroke. On a 10MB JSONL record that blows the 8ms budget independently of wrap. The fix is bounded backwards/forwards rope char iteration; it is out of scope but must not be forgotten.

## Page up / down

Currently unbound, with `default_keymap_tests.rs:391-396` asserting they stay unbound because "paging is the viewport's business". Under wrap they become the clearest possible row motion and are now computable: `RowViewport::page` returns `first_row ± (rows_visible - 1)` (the −1 gives the standard one-row context overlap), the caret moves to that row at the sticky cell, and the viewport follows. They are bound, added to `uses_sticky_columns` (`dispatch.rs:250-262`), and that test assertion is deleted. Omitting them from `uses_sticky_columns` would silently reset the column on every page — the motion still works, it just loses the column, with no test failure.

## Click-to-position

`pixel_to_position_rows`: `row = row_at_y(y)`, then `cell = floor((x - gutter - text_offset + scroll_x) / char_width)`, then `position_at(row, cell)` which clamps to `caret_limit(row)`. Three things this fixes that the current `pixel_to_position` (`mouse.rs:547-563`) gets wrong: it no longer adds a screen row to `viewport.first_line` and calls the result a document line; it no longer clamps the column against the wrong line's length; and `position_at` walks the row's actual cell widths rather than dividing by a constant `char_width = line_height * 0.6`, so clicks on CJK and tabs land on the right character for the first time.

Click affinity: a click whose `cell` exceeds `caret_limit(row)` on a non-final row sets `RowAffinity::Trailing`, so the caret renders at the end of the clicked row rather than jumping to the start of the next one. Every other click sets `Leading`.

`hit_test_fold_indicator_rows` returns `line_of_row(row_at_y(y)).line`, which is the first fold-correct gutter hit test in the crate — the existing one (`mouse.rs:371-378`) is already wrong whenever anything above the click is folded.

## The sticky column under wrapping — the five validity keys

The reusability conjunction at `navigation.rs:116-122` is today `!sticky_dirty && sticky_state == cursor && sticky_revision == revision && len matches`. Wrap width is not a property of the cursor and not a property of the document revision, so a window resize, a font-size change, a gutter-width change or a wrap toggle all change which row a caret sits on and what its cell is while leaving `CursorState` and `Document::revision()` byte-identical. The stale cell is then judged reusable.

That is the same shape as the two bugs already fossilised here — the revision guard (`mod.rs:145-150`) and the `sticky_dirty` flag (`mod.rs:157-160`), both guards against *state that compares equal but means something different*. Wrap is the third instance, so it gets the third guard: `sticky_layout: Option<LayoutGeneration>` as a **fifth clause**, where `LayoutGeneration` is bumped by every edit, every `WrapParams` change and every fold change.

**Undo restoring a cursor into re-wrapped text.** `revalidate_vertical_columns` (`mod.rs:376-381`) is the one path that deliberately does *not* reset — it clears `sticky_dirty` and re-stamps `sticky_revision` on cursor-state equality, which is what makes a multi-cursor block survive an undo. It keeps doing exactly that, and gains one clause: if `sticky_layout != current_generation`, the **cells** are dropped while the cursor state is left alone. The next vertical move then reseeds by measuring the restored caret's actual cell — which is the right answer, not a regression. The temptation to "just also reset here" would regress the behaviour the function exists to protect, and is explicitly rejected.

**Cursor merges.** Under wrap, two carets on different rows of the same document line collapse to one `Position` more often, so the `cursor_count() != count` branch at `navigation.rs:92-99` that destroys the whole snapshot fires more often. It is left as-is: destroying and reseeding by measurement is cheap and correct; reconciling positionally is not possible once the alignment is gone. The `HashMap<Position, usize>` at `multi_cursor_verbs.rs:276-292` keeps its documented collision-overwrite behaviour, now storing cells rather than columns; it is keyed on `Position`, which is still the right key because a `Position` has exactly one `(row, cell)` for a given affinity.

## Affinity, once more

One `RowAffinity` on `KeyboardHandler`, shared by all carets, defaulting to `Leading`, reset by the same `reset_vertical_state()` sites that already exist. It is deliberately not per-caret and deliberately not inside `Position`/`Selection`/`CursorState`: putting it there would change `Position`'s `Eq`/`Hash` (breaking the multi-cursor map), change `Position::advanced_through` (the command-inversion source of truth, where a wrong result makes undo delete the wrong range), and change every serialized cursor. That blast radius buys a cosmetic improvement on a case — multiple carets sitting on distinct break columns with mixed affinities — that arises rarely. Listed as a weakness.

## Performance

## Cost per edit

`RowIndex::apply_edit(rope, LineEdit { first_changed, lines_removed, lines_inserted })`, called from `apply_command_internal`:

1. `RowSums::splice` — remove `lines_removed` entries, insert `lines_inserted`. The blocked layout (1024 lines per block, `u32` per line) makes this a memmove of at most 4KB (~200ns) plus a delta into the block-level Fenwick.
2. Remeasure the `lines_inserted + 1` touched lines exactly, via `break_scan` over the rope slice.
3. Bump `LayoutGeneration`.

Measured cost:
- **Typing one char on a 200-char line:** ~200 `CellWidth` lookups (a table probe each) + one Fenwick point update over `log2(n/1024)` levels. **< 1µs.** Against an 8ms budget this is noise.
- **Inserting a newline in a 1M-line file:** the 4KB memmove + one block-sum delta. **< 2µs.**
- **Typing at the *end* of a 10MB single JSONL line:** the `Sparse` representation stores a checkpoint `(row, char_col, byte_col)` every 64 rows, so the rescan starts from the last checkpoint at or before the edit. **< 50µs.**
- **Typing at the *start* of a 10MB single line:** full rescan, 10M width lookups, **10–30ms**. This is the one real cliff. Mitigation: only the rows up to the end of the current viewport's row window are rescanned synchronously; the tail is handed to `sweep`, so `total_rows()` is an estimate for one or two frames while everything on screen stays exact. Stated as a weakness, not hidden.

## Cost per resize / font change / wrap toggle

`set_params` marks every block stale and bumps the generation. No measurement happens synchronously.

- **On-screen content is always exact**: `line_of_row`/`rows_of_line` measure the block they touch before answering, so the viewport's blocks are brought current on the first query of the frame.
- **The rest is swept**: `sweep(rope, budget_lines)` remeasures from a cursor, called once per frame with a budget the face chooses. At ~100–300 MB/s of `CellWidth` throughput, a 10MB file resweeps fully in 30–100ms (a handful of frames); a 1M-line source tree file in well under one frame.
- **While the sweep is pending**, stale blocks retain their previous-generation row counts, so `total_rows()` is an *estimate* and `is_exact()` returns `false`. The only visible consequence is a scrollbar whose extent settles over a few frames. This is stated in the API docs, not left implicit.

## Cost per frame

Nothing on the render path is `O(document)`:

| Operation | Cost |
|---|---|
| `line_of_row(first_row)` — the viewport anchor | `O(log(n/1024))` Fenwick descent + one ≤1024-entry `u32` scan ≈ **400ns** |
| `rows_of_line(d)` — one per visible line | same, ≈ 400ns each, ~50 visible lines ≈ **20µs** |
| `total_rows()` | **O(1)** |
| `prepare(rope, visible_rows)` | warms `LineWrap` for the visible lines; a cache hit is free, a miss is `O(line_len)` — but only for lines actually on screen |
| `place(caret)` / `position_at(click)` | **O(1)** given a warm `LineWrap` (binary search over break columns) |
| `query_byte_range` | two `line_of_row` calls + two `rope.line_to_byte_idx` ≈ **1µs** |
| fold toggle → `on_folds_changed` | `O(F log F)` coalesce + `O(F log n)` range sums. F is tens. **< 10µs** |

The per-frame path uses only the `&self` Tier-1 API, so it does not contend with the `&mut` cache.

## What is cached and what invalidates it

| Cache | Invalidated by | Cost of invalidation |
|---|---|---|
| `RowSums` (4 bytes/line; 1M lines = **4MB**) | `apply_edit` (point/splice), `set_params` (all blocks stale) | O(log) / O(1) mark |
| block-level Fenwick (n/1024 entries; 1M lines = 4KB) | same | O(log) |
| `LineWrap` LRU (bounded at 4096 lines **or** 1MB of break data, whichever first) | `apply_edit` evicts the touched lines; `set_params` clears it entirely | O(1) / O(cache) |
| `Sparse` checkpoints for long lines (rows/64 entries; a 10MB line at 100 cols = 1562 entries ≈ 19KB) | truncated at the edit's char column | O(1) |
| `FoldRowSums` (F entries) | `on_folds_changed` **and** `apply_edit` (row counts inside folds move) | O(F log n) |
| sticky cells on `KeyboardHandler` | `LayoutGeneration` mismatch | O(1) |

Two invalidation hooks are load-bearing and easy to miss. **`apply_command_internal` (`core.rs:848-879`) must call `apply_edit`** — it is the single funnel every keyboard, mouse, IME, paste and host edit passes through, and it currently does not touch `fold_state` at all. Hooking only `set_content` (`core.rs:219`) and `set_language` (`core.rs:233`), as the fold module does, would give the wrap cache exactly the fold module's staleness discipline: stale `usize` line numbers that stay in range and look sane. **`apply_edit` must also rebuild `FoldRowSums`**, because an edit inside a folded region changes how many rows that fold hides even though the fold's line span is unchanged.

## Structure choice, justified

`RowSums` is a blocked prefix-sum vector with a Fenwick over block sums, not a balanced tree. A plain Fenwick cannot splice (a mid-document line insertion shifts every subsequent index); a B-tree would be asymptotically cleaner but is several hundred more lines and a harder invariant to test. The blocked vector gives O(B) memmove on splice, O(log(n/B)) + O(B) on query, and O(log(n/B)) on point update, with B = 1024 chosen so the memmove is one 4KB page. The pathological case — insert-at-front on a 10M-line file — costs ~10k block-sum fixups (~5µs per edit), which is acceptable and is stated as a weakness rather than papered over.

## Test strategy

Every claim below is a named `#[test]` in `layout/tests/`, with the one permitted `#![allow(clippy::unwrap_used, clippy::expect_used, clippy::panic)]` at the top of `tests/mod.rs`. A shared fixture corpus (`tests/corpus.rs`) is swept across widths 1..40 and both wrap modes; no new dev-dependency (no `proptest`) — the generators are deterministic and checked in, so a failure is reproducible from the test name alone.

## Structural laws (`tests/break_scan.rs`, `tests/row_index.rs`)

1. **Partition law.** For every corpus line × every `WrapParams`: the union of `row_columns(i)` over the line's rows is exactly `0..=line_len`, contiguous, non-overlapping, with strictly increasing starts. Catches gaps at word breaks (where trailing spaces are silently dropped from every row's range) and overlaps at character breaks.
2. **Round trip.** `position_at(place(pos, Leading)) == pos` for **every column of every corpus line at every width**. And `place(position_at(row, cell))` normalises to `(row, cell')` with `cell' <= cell`. This is the test that fails the moment `caret_limit` and `row_columns` are collapsed into one value.
3. **Monotonicity.** `line_of_row` is non-decreasing in row and `rows_of_line(d).start` is strictly increasing over visible `d`. Fails if a line ever produces zero rows.
4. **Row-count ceiling.** `rows(line) <= line_len + 1` for every line at every width — the scanner's own bound, asserted from outside, so a rule regression fails a test instead of hanging the render thread.

## The named hard cases (each its own regression-named test)

5. `wrapped_line_whose_last_row_is_exactly_full_emits_no_trailing_row` — width exactly `W` → **1 row**; width `W+1` → 2 rows with a 1-cell second row; width exactly `2W` → **2 rows**. The `ceil(width/W)` implementation fails all three.
6. `no_row_is_empty_unless_the_line_is_empty` — swept across the whole corpus.
7. `caret_at_a_break_column_resolves_by_affinity` — for every break column `c` of every wrapped corpus line: `place(c, Leading).row == i`, `place(c, Trailing).row == i-1`, and `position_at` maps **both** back to `c`.
8. `tab_is_atomic_across_a_wrap` — `"a\tb"`, `"\t\t\t"`, `"{\t\"k\":1}"` at `tab_width ∈ {2,4,8}` × widths 1..12: the tab is never split, and the row containing it never exceeds `effective` cells unless the tab is alone on the row.
9. `tab_stops_are_anchored_at_the_row_start_not_the_line_start` — a tab on a continuation row expands relative to the row's screen column zero, including the continuation indent. This is the cross-face agreement point for tabs.
10. `double_width_char_that_does_not_fit_starts_the_next_row` — `"aaa世"` at `W=4` → `["aaa","世"]` with one unused cell on row 0. At `W=1` → four rows, the last overflowing to 2 cells.
11. `width_one_and_width_zero_terminate` — the whole corpus at `columns ∈ {0,1}`; asserts termination, the row-count ceiling, and that `columns == 0` degenerates to the wrap-disabled identity rather than reaching the scanner.
12. `zero_width_chars_never_start_a_row` — `"e\u{301}"`, `"a\u{200B}b"`, and `"👨\u{200D}👩\u{200D}👧"` at widths 1..6: no break after a ZWJ or a variation selector, no split between a base and its combining mark.
13. `folded_start_line_keeps_all_its_rows_and_the_placeholder_hangs_on_the_last` — a wrapped line that is also a fold start.

## Composition with folds (`tests/folds.rs`)

14. **Total-rows law.** For randomised fold sets, `total_rows() == Σ rows(d) over all d where !fold_state.is_line_hidden(d)`. Run explicitly **including nested and overlapping regions**, which `fold_all` (`fold_state.rs:469-474`) produces on any real source file. This test is the guard the fold module does not have: it fails immediately if the coalescing step is dropped, because `LineMapping::build` (`fold_state.rs:70-79`) sums nested spans unconditionally and double-counts.
15. **Agreement with the fold line space, restricted.** When the active folds are pairwise **disjoint**, `line_of_row(rows_of_line(d).start).line == d` and the row order agrees with `document_to_visual_line` order. The restriction is deliberate and documented in the test body: under nesting the row space is right and `FoldState`'s line space is wrong, so an unrestricted assertion would be asserting a bug.
16. `fold_toggle_does_not_invalidate_any_measurement` — instrument `WrapIndex` with a measure counter; toggle folds repeatedly and assert the counter never moves. This is the structural property the whole doc→row (rather than doc→visual→row) composition exists to buy.

## Invalidation (`tests/row_index.rs`) — the class of bug this codebase keeps hitting

17. **Edit equivalence.** For a scripted sequence of inserts, deletes, newline insertions, multi-line pastes and undos, assert after **every** step that the incrementally maintained `RowIndex` equals one rebuilt from scratch — field by field, including `total_rows`, every `rows_of_line`, and `FoldRowSums`. This is the test that would have caught "fold boundaries are never updated on edit", and it is the reason `apply_command_internal` must call `apply_edit`.
18. `edit_inside_a_fold_updates_the_folds_row_sums` — a fold's hidden *row* count changes when text inside it is edited, even though its line span does not. Naive implementations rebuild `FoldRowSums` only on fold toggles and silently drift.
19. `sweep_converges_and_is_exact_when_complete` — after `set_params`, drive `sweep` to `Complete` and assert equality with a from-scratch rebuild, and that `is_exact()` flips exactly once.
20. `queries_during_a_pending_sweep_are_exact_for_the_viewport` — measure-on-demand actually fires for the queried block.

## Motion (`tests/motions.rs`)

21. `down_on_the_last_document_line_moves_to_the_next_row_not_the_document_end` — the single case a naive port of `vertical_move` gets wrong.

## Stated weaknesses (self-reported)

**1. Cell-based wrapping assumes a monospace text face.** The kernel decides breaks in `unicode-width` cells; the GPU faces resolve cells to pixels through a single `char_width`. With a proportional font the breaks are wrong in pixels — rows under- or overflow the content width. Iridium sets `Family::Monospace` at every call site (`text.rs:212`, `:267`, `:288`), so this is aligned with the product, but it is a hard architectural boundary. The alternative — asking cosmic-text for break points — is pixel-exact on the GPU faces, can never agree with the terminal, and leaves the kernel unable to answer any layout question headlessly. I chose cross-face agreement over pixel fidelity, and a proportional-font face would have to accept disagreement with the terminal.

**2. Two coordinate vocabularies now coexist permanently.** "Visual line" means folds; "screen row" means wrap. That is one more concept than a clean-slate rename would need, and it is a standing invitation for a future reader — or a future agent — to assume "visual" means wrap. The competing design (rename the fold pair to something fold-explicit, take a compile error at all six Rust call sites, deprecate the two napi names with shims) is genuinely better on this axis: a rename is loud and a redefinition is silent. I traded that loudness for zero breakage across the napi/wasm boundary, an untouched checked-in `pkg/iridium_bindings.d.ts`, and no re-interpretation of persisted `Viewport` state. Reasonable people would choose the rename. The mitigation here is documentation discipline, which is the weakest kind.

**3. The row space and the fold line space disagree under nested folds — and the row space is the one that is right.** Because the row layer composes doc→row through `is_line_hidden` plus coalesced intervals rather than through `FoldState`'s prefix sums, it does not inherit the double-count that `LineMapping::build` (`fold_state.rs:70-79`) produces when `fold_all` folds nested regions. So after `fold_all` on a real source file, the gutter (line space, wrong) and the text (row space, right) will disagree. A design that reused `FoldState`'s sums would be self-consistent and uniformly wrong. I chose visibly-half-right, and made test 14 fail loudly on nesting — but until `LineMapping::build` is fixed to coalesce, this ships a *visible* inconsistency where today there is an invisible one. That fix should land **before** the wrap work, or the wrap work is validated against a wrong baseline.

**4. A single global caret affinity, not one per caret.** Multiple carets sitting on distinct break columns with mixed affinities will render some of them on the wrong side of a wrap. Fixing it properly means widening `CursorState` or `Position`, which changes `Position`'s `Eq`/`Hash` (breaking the `HashMap<Position, usize>` at `multi_cursor_verbs.rs:276`), touches `Position::advanced_through` (where a wrong result makes undo delete the wrong range), and changes every serialized cursor. That is exactly the blast radius the angle refuses, so this is the angle's cost, paid in a cosmetic defect.

**5. Editing at the head of a multi-megabyte single line costs a full remeasure of that line — 10–30ms for 10MB.** The `Sparse` checkpoint scheme only helps for edits at or after a checkpoint. The proper fix is a per-line incremental break structure with local repair, which is a second rope-like data structure and a large amount of code for a case that arises only when a JSONL record is *edited*, not read. The chosen mitigation (measure synchronously only to the end of the viewport's row window, sweep the tail) hides the latency but makes `total_rows()` an estimate for a frame or two.

**6. `RowSums` is a blocked prefix-sum vector, not a balanced tree.** Insert-at-front on a 10M-line file costs ~10k block-sum fixups per edit (~5µs). Acceptable, not asymptotically clean, and it will look bad in a synthetic benchmark someone eventually writes.

**7. The diff is substantially larger than the feature.** `input/mouse.rs` (992 lines) must be split into a directory module before the three row-aware siblings can land, `render/viewport.rs` (696) should be split to accept one deduplicated helper and to shed its six non-test `#[allow]` cast suppressions, and `editor/core.rs` is already several times the cap and gets ~70 lines worse. None of those violations are caused by wrap; all of them are surfaced by it. A reviewer will see a large diff for a feature I am describing as minimally invasive, and that tension is real.

**8. Zero-width and ZWJ handling is a local heuristic, not grapheme segmentation.** "Zero-width chars glue to their predecessor" plus "never break after ZWJ or a variation selector" covers combining accents and simple emoji-ZWJ, but family emoji, flag sequences (regional indicator pairs) and skin-tone modifiers can still break mid-cluster. Adding `unicode-segmentation` would fix it at the cost of a second Unicode table and a per-char cluster state machine inside the hot scanner. Terminals themselves disagree about these widths, so "correct" is partly undefined — but that is an explanation, not a defence.

**9. `EditorConfig::word_wrap`'s default flips from `false` to `true`.** Every host constructing `EditorConfig::default()` changes behaviour. That is the ratified decision, but it is a behaviour change smuggled inside a default value, and configs serialized before the flip carry an explicit `false` and will keep wrap *off* forever unless the host acts — which is arguably the wrong outcome for the very users the decision was made for.

**10. The sticky column becomes a sticky cell even with wrap off.** Vertical motion through tabs and CJK changes behaviour today, in a build where wrap is disabled. It is a fix, and it is pinned by test 30, but it is a behaviour change that no existing test asserts and that a host may depend on. The alternative — column-sticky when wrap is off, cell-sticky when on — is two modes of the same mechanism, which is worse.

**11. `RowIndex`'s column-space queries take `&mut self`.** `place`, `position_at`, `row_columns` and `caret_limit` warm a cache, so a face holding `&EditorState` cannot call them without a `prepare(&mut …)` call earlier in the frame. Tier-1 (row/line space) is `&self`, so nothing per-frame is blocked, but the two-tier API is a real ergonomic wart and an easy thing to get wrong from a face. The alternatives are interior mutability (a `RefCell` whose `borrow_mut` is a latent panic in a crate that bans panics) or eager full measurement (which reintroduces the resize cliff).

**12. Sub-row scrolling remains structurally supported and unexercised.** `RowViewport::row_offset_px` mirrors `Viewport::scroll_offset_y`, which today is never assigned a non-zero value anywhere in the crate. I have kept the field and the sign convention, so the same dormant-and-untested state now exists in two places rather than one.

## Best ideas from the designs that lost

Graft these rather than discard them with their designs.

### From `lazy-windowed`

Wrap is computed only for the viewport window plus overscan and never for the whole document, because the owner's files are multi-hundred-megabyte JSON/JSONL where a full wrap pass costs seconds per resize and tens of megabytes of index — the exact failure mode (memory bloat, stalls) that Iridium exists to escape. The enabling move is to stop indexing rows globally: scroll position becomes a `ScrollAnchor { doc_line, row_in_line, subrow_px }` instead of `Viewport::first_line`, so a row's identity is a document coordinate plus a small local offset, and no absolute row number ever exists. Greedy wrap is prefix-determined, so a bounded `WrapWindow` of at most `visible + 2×overscan` `RowSlice`s (~26 KB, document-size-independent) can be extended, re-wrapped, and edit-patched in O(window) — ~80 µs measured-scale for a 540-row 4K window, 1% of a 120 fps frame. Total row count, which the design refuses to compute, is answered three ways: the scrollbar runs on byte fraction (O(log n), monotone, exact at both ends, and strictly better than the current wasm face which uses a stale previous-frame count); the minimap is declared document-line space forever; and "go to row N" is deleted as a verb because every external location source — grep, compilers, LSP, search — speaks document lines, so absolute rows only ever existed as a scroll artifact. Anyone who insists on a total gets a `RowEstimate { measured_rows, measured_bytes, estimated_total }` that cannot be mistaken for a `usize`. The three coordinate spaces get newtypes (`DocLine`, `UnfoldedLine`, `ScreenRow`) and the fold pair is renamed off the word "visual", turning every silent break catalogued in the map into a compile error.

- **Worth stealing:** ScrollAnchor { doc_line, row_in_line, subrow_px } replacing Viewport::first_line — deleting the absolute row index rather than making it wrap-aware. Because a row's identity becomes a document coordinate plus a small bounded local offset, no global row space ever has to be built, so every downstream question is either O(1) against the window or a compile error at the five external readers of the removed field (mouse.rs:380,549; minimap/types.rs:143; minimap/renderer.rs:294; wasm.rs:1871) — the exact sites the map proves would otherwise fail silently, zero-error on code files and wrong only on JSONL. It is also the only proposal here that makes session persistence survive a font change or resize, since a saved row index is meaningless after either. The close second, and the thing that makes the anchor affordable, is composing fold BEFORE wrap: a fold toggle then changes which lines are visited and never how a line breaks, so every cached per-line row ladder survives a fold/unfold cycle at zero break scans, and the design sidesteps the pre-existing nested-fold double-count in LineMapping::build (fold_state.rs:70-79) entirely rather than amplifying it by the wrap factor. Any competing design should steal both regardless of who wins.
- **Why it lost:** StickyX is specified as "the horizontal offset from the row's TEXT ORIGIN in width units", and RowSlice carries leading_indent as a field separate from col_start — so text origin means after the indent. With the design's own stated default WrapIndent::MatchIndentPlus(0), pressing Down inside a wrapped indented line moves the caret sideways by the indent width.
