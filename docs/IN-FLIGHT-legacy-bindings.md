# #64 — the legacy `iridium-bindings/ts` tree

**Finding, verified by hand. Needs one ruling from Tom before anything is
deleted, because deleting it withdraws something two config files call
"supported".**

## What the task note said, and what is actually true

The note reads *"21.9 MB tracked grammar bundle that nothing imports, and the
builder writes to it"*. Both halves are true, and the situation is larger than
one file.

## The whole tree is dead, not just the bundle

`crates/iridium-bindings/ts/` — 21 MB tracked — holds `controller/index.ts`,
`element/index.ts` and `syntax/{index,core.gen,grammars.gen,queries}.ts`.

**Nothing anywhere imports any of it.** Every reference to the name
`iridium-bindings` in the repo, excluding `node_modules` and the package's own
`package.json`, is a *vite alias declaration*:

```
examples/web/vite.config.ts:25            "iridium-bindings"          → ts/controller/index.ts
examples/web/vite.config.ts:26            "iridium-bindings/wasm"     → pkg/iridium_bindings.js
examples/web-component/vite.config.ts:18  "iridium-bindings/element"  → ts/element/index.ts
examples/web-component/vite.config.ts:19  "iridium-bindings/wasm"     → pkg/iridium_bindings.js
examples/web-component/vite.config.ts:20  "iridium-bindings"          → ts/controller/index.ts
```

They are aliases for names no source file uses. Both examples import
`@iridium/core/*` exclusively. The `/wasm` aliases point at `pkg/`, which is
the wasm build and is *not* part of this — only the `ts/` tree is.

## It is a fork that fell a long way behind

`packages/@iridium/core/src/` is the live copy. Comparing file by file:

| file | legacy | live |
| --- | --- | --- |
| `syntax/queries.ts` | 34,031 | **byte-identical** |
| `syntax/index.ts` | 14,890 | 15,199 |
| `element/index.ts` | 6,365 | 10,869 |
| `controller/index.ts` | 34,707 | **65,800** |

The controller is **half the size of the live one**. It is a snapshot from
before roughly half the current feature set — no palette, no undo-tree
navigation. "Still supported", as the vite comments call it, is a claim rather
than a fact: anyone reaching for it would get an editor missing the two
features most recently built.

## The builder writes only to the dead copy

`packages/tree-sitter-builder/build.ts:88`

```ts
const OUTPUT_DIR = join(__dirname, "../../crates/iridium-bindings/ts/syntax");
```

and writes `core.gen.ts`, `grammars.gen.ts` and `queries.ts` there
(`:411-413`), printing all three paths as its output.

**This is the part that is a defect rather than clutter.** Rebuilding the
grammars reports success, writes 21 MB, and changes nothing that runs — the
live bundle at `packages/@iridium/core/src/syntax/grammars.gen.ts` is
untouched. There is no copy step; that file was last written on 30 July and
the legacy one on 14 January.

## The sizes do not match, and that matters

Live `grammars.gen.ts` is **2.0 MB**; the builder's output is **21 MB**. They
are not the same artefact built twice — so *repointing `OUTPUT_DIR` at the
live path is not a safe mechanical fix*. It would replace a 2 MB bundle with a
21 MB one and put ten times the weight into the browser payload. Whatever
produces the 2 MB file is not this builder, and that has to be found before
the builder is repointed.

## ⭐ ANSWERED, 8 Aug — and the paragraph above is half wrong

The open question was *"what produces the live 2 MB bundle today?"*. It is the
**same builder, from the same run**. Proved rather than inferred:

| | live (`packages/`) | dead (`crates/`) |
| --- | --- | --- |
| `Generated by:` | `packages/tree-sitter-builder` | `packages/tree-sitter-builder` |
| `Date:` | `2026-01-14T00:12:28.941Z` | `2026-01-14T00:12:28.941Z` |
| header note | "(gzip-compressed)" | — |
| `"rust"` payload, decoded | 114,311 B, magic `1f8b0800` | 1,113,644 B, magic `0061736d` |

`1f 8b 08` is a gzip header; `00 61 73 6d` is `\0asm`, the WebAssembly magic.
Gunzipping the live entry yields **1,113,644 bytes whose SHA-256 equals the
dead entry's, byte for byte**. Ratio 9.74×, which is what gzip does to wasm.

So: **one artefact, two encodings.** The live file is the same bundle gzipped
and base64'd, with a matching `DecompressionStream("gzip")` step added to
`decodeGrammar` (`grammars.gen.ts:66`, and the same in `core.gen.ts:20`).

### What that makes the real defect

⚠️ **`build.ts` can no longer produce the live artefact.** It contains **no**
gzip step — `grep -n "gzip\|compress\|zlib"` over the file returns nothing —
and the loader it emits is raw-only: `atob` into a `Uint8Array` and no
decompression (`:306-312`). Its output is internally consistent, just
uncompressed.

The compression step **and** the gunzip loader template were both lost from the
builder at some point after 14 January. Nothing recorded it, because the only
evidence either ever existed is inside a file stamped `DO NOT EDIT MANUALLY`.

⭐ **The live bundle is unreproducible from the tree.** Regenerate the grammars
today and the browser payload silently goes **2.1 MB → 21.9 MB** with a green
build and no warning. That is a worse failure than writing to a dead path,
because writing to a dead path changes nothing.

### The corrected recommendation

Not "find the other producer" — there is no other producer. The second question
has a specific answer:

1. **Restore the gzip step and the gunzip loader template in `build.ts`.** The
   evidence for what they looked like is in the emitted files: gzip the wasm
   before base64, and emit the `DecompressionStream("gzip")` reader that
   `grammars.gen.ts:60-85` already contains.
2. **Then** repointing `OUTPUT_DIR` is the safe mechanical fix the paragraph
   above says it is not, because the builder would reproduce the live artefact
   rather than a tenfold inflation of it.

⚠️ **Not done here, and priced rather than guessed at.** Verifying a change to
`build.ts` means running it, and running it clones nineteen grammar
repositories over the network and writes 21 MB. An unverified change to a build
script whose output is a tracked multi-megabyte artefact is exactly what the
standard forbids, and cloning nineteen repos onto a shared box is not a call to
make unasked. The finding is what unblocks the ruling; the change is one step
behind it and needs a green light on the clone.

## The ruling needed

**Does the legacy `crates/iridium-bindings/ts/` tree go?**

Recommend **yes, delete the tree and the five vite aliases**. It has no
importers, it is a stale fork of code that has since doubled, and keeping it
means every grammar rebuild silently writes 21 MB nobody reads.

If it goes, `OUTPUT_DIR` still needs an answer — and as of 8 Aug that second
question is **answered**, so it is no longer a question so much as a queued
change. See the section above: the same builder produced both files, gzip and
the gunzip loader have since been lost from `build.ts`, and restoring them is
what makes repointing safe.

⚠️ **Order matters, and it is the opposite of the obvious one.** Deleting the
tree first leaves `OUTPUT_DIR` pointing at nothing, so the builder breaks
outright. Repointing first, *without* restoring gzip, ships a 21.9 MB browser
payload on the next rebuild with a green build and no warning. **Restore gzip →
repoint → delete** is the only order in which no step is worse than the state
before it.

The earlier suggestion here — make the builder fail loudly in the interim — is
withdrawn. It was the right call while the producer was unknown; it is not now,
because a builder that refuses to run is a worse interim than one that writes
to a path the delete is about to remove anyway.

⚠️ **What is still Tom's, and one thing that is now smaller.** The deletion is
his: withdrawing a surface two config files call supported is a product
decision, and 21 MB of tracked history is not a deletion to make on my own
reading of a grep. But the *risk* attached to it has dropped — the second
question no longer holds an unknown, only a step.

**One green light I do need**, separate from the ruling: restoring gzip cannot
be verified without running the builder, which clones nineteen grammar
repositories. That is a network and disk call on a shared box, not a code
decision, and it is the only thing standing between here and a finished fix.
