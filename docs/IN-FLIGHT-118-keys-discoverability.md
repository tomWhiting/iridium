## 1. ⭐ THE ASK — every binding must already be listed in `config.toml`

Tom, verbatim:

> "Last time I noticed in that was that you had to add the key bindings
> yourself and you don't know what they are. So we need to make sure that the
> key bindings thing has all of the key bindings available to change. So you
> need to have them all already listed there because you couldn't possibly
> expect somebody to know the name of all the key bindings."

**He is right, and #91 did not fix this.** #91 made a `[keys]` line *work*. It
did nothing about a user being able to **find out what to write**. Today
`config.toml`'s `[keys]` section is a hand-written prose block (`KEYS`, a
`&str` constant at `crates/iridium-config/src/template.rs:99,165`) with a
handful of illustrative examples. Every real binding — the ~69 editor defaults,
the 42 explorer defaults, every host and workspace command — is discoverable
only by reading Rust source.

### Where it goes

`crates/iridium-config/src/template.rs`, `default_config()` at `:64`. The
`[editor]` block is already generated by serializing `EditorConfig::default()`
and commenting each line out (`:67-97`). **`[keys]` must be generated the same
way**, from the actual default keymaps rather than from a prose constant.

### The shape to build

Emit every binding **commented out**, grouped, with its command id:

```toml
[keys]
# ctrl+shift+k = "edit.deleteLine"          # Delete Line
# ...
# --- File explorer (only while the panel has focus) ---
# tab = "explorer.beginEdit"                # Edit Rows As Text
```

⛔ **Commented out, not live.** A live block would freeze today's defaults into
every user's file: change a default in code and the shipped file silently pins
the old one. Commented, the file is a **menu** — defaults stay authoritative in
code, and uncommenting a line is exactly "change this one".

### Sources to enumerate — do NOT hand-write the list

- editor defaults: `iridium_editor::commands::default_non_modal_keymap()`
  (69 bindings, `DEFAULT_KEYMAP_BINDING_COUNT`)
- explorer defaults: `iridium_panel::explorer::default_keymap()`
  (42 bindings, `DEFAULT_BINDING_COUNT`) — **⚠️ `iridium-config` does not
  depend on `iridium-panel` today.** Either add the dep or have the face
  contribute its layer. Decide and record it.
- the *unbound* commands matter too: `transform.*` and most `ast.*` are
  palette-only by design, and a user who wants a key for them cannot guess the
  id. List them under a "no default key" heading, using
  `registry.palette_order()` minus what is bound.
- ⚠️ Use `KeyBinding::display_sequence()` for the left-hand side — it is the
  round-trippable spelling `KeyBinding::parse` reads back, so a line the user
  uncomments is guaranteed to parse. Do **not** use a prettified label.
- ⚠️ Mode-scoped commands need no mode written: #91's D-2 derives it from the
  command. Say so in a comment in the file, or users will think they must.

### Proof obligations

- every emitted line round-trips: uncomment it, parse it, and the binding that
  comes back names the same command and the same sequence;
- the generated file parses clean with **zero** `Problem`s;
- the count in the file equals the count in the keymaps (a ratchet, so a
  binding added in code but missing from the template fails);
- `create_if_absent` still refuses to clobber an existing file.

  Vim as "needs a new kernel mechanism" against Helix as "data only" — but once
  that mechanism exists *by his ruling*, **both grammars are data**. D-1 was
  written as though the mechanism were still in question, which his ruling had
  already settled the day before.

### What to do about it

1. Retire D-1 in `docs/IN-FLIGHT-113-modality.md` — replace it with the finding
   above rather than deleting it, so the mistake is legible.
2. `#113` is **not blocked**. Steps 4 and 5 proceed. Remove "blocked on the
   grammar ruling" from the task and from the handoff's live-state section.
3. G-6 (`the config keymap has no modes and no selector`) is the *real*
   remaining gap, and #91 only half-closed it: mode-scoped **panel** commands
   derive their mode from `CommandMeta`, but a modal keymap binding **editor**
   commands in a `normal` mode still has no spelling in `[keys]`. That is a
   config-format question, and it is the thing that actually needs deciding —
   not which grammar.
4. Whichever keymap gets authored first is a **file**, not a fork. Shipping
   both eventually costs two data files and no kernel change.
