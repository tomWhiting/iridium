# AWL — the ground, answered at the bytes

Answers from **Vesper Lynd** (owner of Aeon) on 7 Aug 2026, read out of the
aion repo rather than from memory. This closes **#67** and unblocks AWL as the
first non-vendored language once the registry step (#63) lands.

---

## 1. It vendors cleanly, and the version worry was unfounded

| | |
| --- | --- |
| Generated by | `tree-sitter-cli` **0.26.10** |
| ABI | `LANGUAGE_VERSION` **15** |
| Runtime here | tree-sitter **0.26.3** — ABI 15 loads |
| `scanner.c` | **none** — `parser.c` is the whole grammar |
| Published crate | **none on crates.io** |

The `links = "tree-sitter"` collision that forced chiron to vendor `parser.c`
for just/typst/wgsl **cannot arise here**: there is no AWL crate to pull a
second `tree-sitter` into the graph. Vendoring the generated `parser.c` and
compiling it with `cc` is not a workaround for AWL, it is the only option, and
it is the same road chiron is already on.

No external scanner is a real simplification. AWL's canonical parser is
indentation-based, but the rev-2 surface gives every block a keyword-led
opening, so the grammar keys off those anchors and stays newline- and
indent-tolerant without one.

**Carry into the manifest:** this grammar is a *presentation layer only*.
`crates/aion-awl` — a hand-written lexer, parser and checker — is the sole
parser used for diagnostics. The tree-sitter grammar must never be treated as a
validity check, which matters the moment anything wants to surface parse errors
from a syntax tree.

## 2. Where to vendor from

- **Source of truth:** `tools/tree-sitter-awl/` in `github.com/ablative-io/aion`,
  at `main`.
- **Public build mirror:** `github.com/tomWhiting/tree-sitter-awl`, which Zed
  fetches at a pinned rev (`8d4d63e…`).

A sha256 gate in `crates/aion-awl/tests/editor_assets.rs` fails the aion suite
if the mirror pin and the in-repo sources disagree, so either is safe. Take the
in-repo one — it is the thing the gate protects.

## 3. Queries — and the mismatch that matters

Shipped in `tools/tree-sitter-awl/queries/`:

| file | Iridium has a `QueryKind` for it? |
| --- | --- |
| `highlights.scm` | ✅ `Highlights` |
| `indents.scm` | ✅ `Indents` |
| `folds.scm` | ❌ **no kind exists** |
| `outline.scm` (in the Zed extension, not the grammar repo) | ✅ `Outline` |

Not shipped: `brackets.scm`, `textobjects.scm`. `injections` is explicitly
`null` in `tree-sitter.json`.

The highlights query is gate-tested upstream — a golden-file smoke test
(`test/awl_hello.highlights.golden` + `highlight-smoke.sh`) and a corpus sweep,
both offered for reuse as Iridium's own vendoring check.

### 3.1 This is the proof that `QueryKind` cannot stay as it is

`query/embedded.rs` matches exhaustively over `(Language, QueryKind)` with **no
wildcard arm**, on purpose: it forces a decision, file by file, about what each
language ships. That property is exactly what a language shipping a *different
subset* breaks. AWL has four of the six kinds, lacks two, and ships a seventh
Iridium has no name for.

So the registry step has to move this from "an exhaustive match over two closed
enums" to "the set of queries a language declares", with a test asserting the
declared files exist rather than a compiler asserting the match is total.

### 3.2 What Iridium would actually miss

Only two of the six kinds have a live consumer. Checked, not assumed:

| kind | non-test consumers |
| --- | --- |
| `Highlights` | 1 |
| `TextObjects` | 1 |
| `Brackets`, `Indents`, `Injections`, `Outline` | **0** |

Four kinds are vendored, compiled and cached for every language, and read by
nothing.

So the answer to Vesper's offer to add `brackets.scm` upstream is **no** —
nothing would read it. The file that would matter is **`textobjects.scm`**,
because it is the only missing one with a consumer.

What its absence costs is narrower than it sounds. Expand/shrink walks the
*tree* — node to parent — and needs no query, so structural selection works in
AWL the day the grammar lands. What `textobjects.scm` adds is the **named**
objects: `selectFunctionInside/Around`, `selectClassInside/Around`,
`selectCommentAround`, and the jump-by-kind verbs. Those are the five captures
the vendored queries carry and no more.

## 4. Manifest fields, ready to write

| key | value |
| --- | --- |
| `name` | `AWL` |
| `grammar` | `awl` |
| `path_suffixes` | `["awl"]` — **`.awl` only**; nothing plays the `tsconfig.json` role |
| `line_comments` | `["// "]` |
| `block_comment` | **none** |
| `documentation_comment` | **none** |

So AWL lands in the same shape as Python, YAML and Bash: a line token and no
block pair. Under the derivation rules already built and tested
(`docs/IN-FLIGHT-manifests.md` §2), `block_comment()` correctly returns `None`
— there is no `documentation_comment` for the fallback to reach.

**One thing to preserve:** AWL's doc comments are *distinct grammar tokens*, not
a naming convention. `///` is item docs and `//!` is document/module header
docs, and the grammar separates `doc_comment` from `comment`. Worth
highlighting differently. Note this is the opposite of Rust's manifest, which
lists `["// ", "/// ", "//! "]` as three *line-comment* tokens and leaves the
distinction to the highlights query.

## What this does not settle

The registry step itself. AWL needs `Language` to stop being a closed enum,
`COMPILED` to stop being a fixed array indexed by `Language::index()`, and
`embedded.rs` to stop being an exhaustive match — all of which is #63, and none
of which AWL causes. It is simply the first language that makes the cost of
*not* doing it concrete.
